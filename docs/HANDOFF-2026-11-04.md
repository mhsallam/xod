## 3. What this session did (v1.2.6 → v1.2.7)

### 3.1 Cascade delete was silently dropping children — fixed (`ISS-037`, `PLAN-032`)

Deleting a parent on JSON or Binary storage removed only the parent row and returned `true`. Cause:
`Delete` resolves children by item code and calls `IOService.TryDeleteRow`, which looked in the
parsed-file cache, then in the raw-page cache — and the raw path is **XML-only** (`TryGetRowFromRawPage`
parses `<Row code="...">` out of the page bytes). On JSON/Binary a cold child page simply answered
"not found", which the caller cannot distinguish from a genuine miss.

Fix: `TryDeleteRow` loads the page through the normal file path (`OpenFileOrCreate`) before reporting
a miss. One owner for the delete, no format special-casing.

Evidence: `tests/Xod.Tests/XodIntegrityTests.cs`, 9 cases (3 formats × shell/hydrated deletes, cold
reopen, exact counts, idempotent double delete); the 40k relational benchmark now passes its
cascade-count validation on all five engines.

### 3.2 Benchmark evidence became reproducible (`PLAN-031`, `TASK-036`)

- Every run now carries a `Stamp`: library version, git commit, working-tree state, runtime, machine,
  CPU, timestamp. `"unknown"` when git cannot be read — never an empty string that reads as valid.
- Results are written to `benchmarks/results/` (committed), named `bench-v<version>-<commit>-<ts>.json`.
- The dashboard's scorecard was hand-typed HTML with frozen numbers and "XOD #1" badges. The public
  dashboard is now the separate `xod-site` repo, built from these files; the old C# HTML generator
  still sits in `benchmarks/XodBench/` and should be deleted rather than fed.
- Old unstamped files are kept in `results/archive/` and explicitly marked *not citable*.

### 3.3 Page cache bounded by memory, not by page count (`ISS-038`, `PLAN-033`)

20 indexed queries over 400k rows took 74 s (JSON) / 100 s (Binary) at 1 GB. The cache held at most
**1,024 parsed pages**; a 1 GB database has ~1,700, and the benchmark's scattered matches touch nearly
all of them, so every query re-parsed (or Brotli-decompressed) a whole page per row.

`CacheFile` is now the only path into the cache and evicts LRU pages until both an entry cap and a
byte budget fit — a quarter of the memory available to the runtime, clamped to 64 MB–4 GB. Page cost
is `LastSavedSize`, a full page assumed while unsaved and as the floor for Binary. **The estimate does
no file I/O** — the first version called `FileInfo` per save and made bulk insert 2.7× slower on its
own.

Same-machine result: Binary 1 GB 20 queries **140,510 ms → 61 ms**, JSON **73,765 → 71 ms**, XML
**4,953 → 112 ms**; bulk insert unchanged (27,225 → 25,700 ms); peak working set 4,896 → 2,763 MB.

### 3.4 Page-size sweep (`PLAN-035`, `TASK-040`)

`XOD_PAGE_SIZE=<kb>` now overrides the 512 KB default in the harness. Findings: **512 KB is the right
default** (wins or ties every XML metric). On JSON/Binary, 64–128 KB pages nearly halve point lookups
(JSON 1,249 → 654 ms; Binary 1,366 → 795 ms) but make indexed queries 25–100× slower and bulk 2–4×
slower. **No default changed.** Documented in `benchmarks/results/README.md`.

## 6. Rules that are not optional here

1. **No `Co-Authored-By`, no tool attribution** in commits, tags or PR bodies. Owner's standing rule.
2. **A number is quotable only when its result file is committed and its stamp is clean.**
3. **Fix the cause, not the symptom.** If a cache or a lock hides a defect, say so; do not special-case
   the format.
4. **Every perf change needs a before/after on the same machine**, and a revert when it does not win.
   The first page-cache attempt in this session was measured at 144 s and reverted; the second shipped
   at 61 ms. Both are in git history, deliberately.
5. **Validate the data, not just the timing.** The harness already refuses a run whose counts, ids or
   graph shape are wrong — keep that discipline when adding a benchmark.
6. Do not push, tag or publish anything outward-facing without the owner's go in the session where it
   happens.

  `SpliceRowInRawPage`), `IndexService*.cs` and `IOService.Files.cs` (page cache, save path).
- **Rank the proposals** by expected gain, risk to correctness, and effort. For each: the mechanism,
  the code you would change, the metric it should move, and how it could regress.
- **Name the experiment** that would prove or disprove it, and the number you expect.
- **Say what you would not do**, and why.

Useful starting points we already know about (do not just repeat them — improve on them):

1. `ISS-039`: row span index for JSON pages, offset/block scheme for Binary, so a point read stops
   costing a whole-page parse.
2. XML point reads: skip `XElement` on cold reads (span → POCO), plus a small row cache with correct
   invalidation. 89 µs/read today.
3. Relational writes: children acquire locks and page decisions one at a time; batching by target page
   should be ~2× on graph insert and 3–5× on cascade delete.
4. Anything you see in the index path: index hydration at open, per-row index maintenance, the
   `RemoveRowElement` path.

Constraints for any proposal: XML, JSON and Binary must all stay correct and pass
`XodIntegrityTests` + `XodCacheTests` + the stress suite (40 tests today); keep the public API;
no format change without a migration story; no dependency on a server.
