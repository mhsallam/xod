# XOD++ Known Issues & Legacy Design Flaws Catalog

This document tracks all known bugs inherited from XOD 1.x (`xod` / `xod.core`) as well as architectural/design issues identified in XOD++ (`xod2`). Each issue is referenced by ID in [`MASTER-TASKS.md`](MASTER-TASKS.md).

| **ISS-044** | Medium | Concurrent reads (`XodContext.Find` read path) | **Reads barely scale with threads**: primary-key lookups over a 50,000-row hot set with no writer ran at 0.70M/s on 1 thread, 1.15M/s on 2 and 1.7M/s on 8 (`XodBench --stress --profile soak --writers 0`, 15 s each, pinned to the performance cores). ~~Eight reader threads used about one core between them, so the readers mostly wait on each other inside `Find`~~ (withdrawn 2026-11-12: that came from Windows' CPU time, which under-reads busy threads here by up to about 15x, `ISS-106`; cycle counts show the eight readers on the processor nearly all the time, spinning in the contended sections). With one writer committing every second, eight readers fell to 0.77-0.86M/s and GC pauses took about 15% of the time. In the 45-minute soak (2M rows, 200k hot, 8 readers, 1 writer committing every second): 409k reads/s, GC pauses 21% of the time, slowest read 856 ms and slowest commit 554 ms - `Flush` takes the engine-wide write lock, so a long commit stalls every reader. The site states measured numbers only, no scaling claim. **Causes (2026-11-12, `TASK-069`, measured):** (1) reads: every `Find` makes seven exclusive acquisitions on four words every reader writes: `IndexService.syncLock` twice (`IsTypeHydrated`, the planner's lookup), `IOService.syncLock` once, and two `ReaderWriterLockSlim`s, whose read enter and exit each take the lock's spin lock. On 8 threads 3.1 of 4.7 microseconds per `Find` are in the two index sections; with every shared section removed (prototype), 8 threads do 2.3x. (2) commit tails: an index snapshot (336 ms at 2M rows) inside `Flush`, under the engine-wide write lock; an update-only workload snapshots because every update re-keys every indexed property, changed or not. (3) GC: that re-keying (gen1) and a page's row map dropped whenever a row grows and rebuilt by the next reader (gen2).
